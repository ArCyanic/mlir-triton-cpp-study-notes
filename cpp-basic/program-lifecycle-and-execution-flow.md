# 程序生命周期流转

本文系统解构 C++ 程序从源码文本到进程消亡的端到端生命周期。核心宗旨在于解构“主函数是一切起点”的直觉认知，顺着编译器、静态链接器、操作系统内核与运行时库的物理交接过程，建立一条前后咬合的因果流转脉络。

深水区重定位代数推导、ELF 双重视图装配与动态链接延迟绑定机制参见 [《二进制链接运行时机理推演》](binary-linking-and-runtime-mechanics.md)。

---

## 1. 运行环境拓扑

在计算机系统的物理实现中，`main()` 仅是用户业务逻辑的介入点。在首行用户代码执行前，操作系统与运行时环境必须先行构筑起虚拟内存页表、建立共享库链接、对齐硬件调用栈，并执行全部全局对象的构造函数；而在主函数返回后，运行时必须逆序析构对象、冲刷文件缓冲区并归还内核资源。

从静态源码文本到动态活跃进程，再到最终消亡，程序经历五个不可逆的物理演进阶段：

```text
========================================================================================
                               程序全生命周期因果流转拓扑
========================================================================================

  [物理输入：C++ 源码文本] (main.cpp / utils.cpp)
          │
          ▼
┌─────────────────────────────────────────────────────────────┐
│ 阶段一：目标文件编译 (Preprocessing -> Compile -> Assemble) │
│   • 物理产物: 包含未决符号的可重定位目标文件 (.o)           │
│   • 未决状态: 单文件编译视界无法获知跨模块函数的真实地址，  │
│               在调用跳转指令中预留四字节全零占位符并记录重定位条目。│
└──────────────────────────────┬──────────────────────────────┘
                               │ 传递未决符号与重定位表 (.rela)
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ 阶段二：静态链接定址 (Symbol Resolution & Relocation)       │
│   • 物理产物: 磁盘静态 ELF 可执行文件                       │
│   • 未决状态: 二进制文件仅为磁盘持久化镜像，缺乏执行上下文，│
│               必须依赖操作系统内核激活为活动进程。          │
└──────────────────────────────┬──────────────────────────────┘
                               │ 触发系统调用 execve(2)
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ 阶段三：虚拟空间装载 (Kernel Loader & Memory Layout)        │
│   • 物理产物: 进程虚拟内存空间 (VMA) 与用户态堆栈参数       │
│   • 未决状态: 虚存建立完毕但代码不可执行：动态符号未绑定，  │
│               全局 C++ 对象未调用构造函数，跳入即崩溃。     │
└──────────────────────────────┬──────────────────────────────┘
                               │ 控制权移交动态链接器与 CRT 入口
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ 阶段四：运行时环境就绪 (CRT Startup: _start -> main)        │
│   • 物理产物: 完成动态重定位、堆栈对齐与 .init_array 构造   │
│   • 状态闭合: 运行时环境彻底就绪，控制权正式跃入 main()     │
└──────────────────────────────┬──────────────────────────────┘
                               │ main() 执行完毕返回退出码
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ 阶段五：运行时销毁退出 (Teardown: exit -> Termination)      │
│   • 物理产物: 逆序执行 .fini_array、冲刷缓冲区、内核销毁 PCB│
│   • 终态归宿: 进程从操作系统彻底注销，生命周期闭合          │
└─────────────────────────────────────────────────────────────┘
```

全篇叙事遵循一条客观因果律：**上一阶段遗留的未决状态与物理约束，必然构成下一阶段系统构件接管与推进的前提。**

工具链与操作系统在各个阶段构筑起紧密的工程契约，用于持续推进上游未完成的物理状态：
- **主函数介入边界**：`main()` 函数在机器视角下只是一个被 C 运行时环境调用的普通函数指针，其参数由内核在栈底初始化，其返回值被运行时捕获用于指导后续资源清理；
- **软硬件环境依赖**：用户代码的平稳运行建立在严密的底层契约之上，包括 MMU 页表对齐、ABI 规定的 16 字节栈对齐、以及动态链接符号解析；
- **状态守恒演进法则**：从源码中的文本符号到最终由 CPU 执行的二进制机器码，每一个信息的物理转换都伴随着确定性的空间布局与地址绑定。

## 2. 目标文件编译

人类依靠具备丰富抽象语法与强类型系统的 C++ 语言来掌控复杂工程，并通过拆分多个源文件实现并行开发与模块解耦；然而底层的 CPU 与内存硬件只认两件事：具备严格内存保护权限的连续物理页，以及具备确定位移的操作指令码。编译阶段的根本使命，正在于将人类的高层抽象语义，物理映射为硬件能够直接接纳的二进制指令与内存布局。

在此映射过程中，编译器前端（如 Clang 或 GCC）与汇编器（如 GNU `as`）受制于两项底层系统的客观硬件约束：

一方面，源码中的数据实体具有异质的生命周期与安全特权诉求——可执行指令必须严防运行期篡改以阻断代码注入，只读常量必须受硬件只读保护以维系语言常属性契约，而初始值为零的大数组若全量落盘则会引发无意义的分发体积膨胀。为了配合操作系统内存管理单元（MMU）后续施加的页面硬件保护，编译系统必须在代码生成的源头，依据存储期与访问权限将数据分类打包，这构成了节区属性契约（2.1 节）的成因。

另一方面，软件工程的模块化诉求要求各个源文件能够独立编译，但这天然切断了编译工具链的全局符号视野。当代码调用其他源文件中定义的函数时，单文件汇编器的指令生成机制直接受阻于目标虚拟内存基址未知的客观事实。为了不中断单文件的翻译流水线，汇编器只得采取工程折中：在机器跳转指令的操作数槽位暂留 4 字节定长占位符，并在重定位节区登记待修补条目，这构成了跨模块未决占位符（2.2 节）的物理必然性。

最终输出的可重定位目标文件（`.o`）因而呈现出双重特征：它既是一组按硬件权限整齐编排的物理节区，又是一份包含未决跳转占位符与重定位记录的目标文件。

### 2.1 节区属性契约

汇编器在输出二进制目标文件（`.o`）时，依据 C++ 变量的生命周期与常量属性，将离散的符号与数据划分至具有严格内存保护权限的独立节区（Sections）。各个节区不仅决定了数据在磁盘文件中的排布方式，更向后续的操作系统装载器声明了运行时所需的物理访问权限：

| ELF 节区名称 | 物理承载内容 | 运行时内存权限 | 磁盘存储机制与优化策略 |
| :--- | :--- | :--- | :--- |
| **`.text`** | 编译生成的 CPU 可执行机器指令流 | 可读、可执行（`R-X`） | 二进制指令实体直接固化在目标文件中，装载时禁止写入。 |
| **`.rodata`** | 字符串字面量、`const` 全局常量与 C++ 虚函数表 | 只读（`R--`） | 实体固化在目标文件中，运行时任何写尝试直接触发硬件段错误。 |
| **`.data`** | 显式初始化且初值非零的全局变量与静态变量 | 可读、可写（`RW-`） | 变量初始二进制数值直接存储在目标文件中，装载时分配物理内存。 |
| **`.bss`** | 未显式初始化或初值为零的全局变量与静态变量 | 可读、可写（`RW-`） | **磁盘零占位**：仅在节头记录字节尺寸，利用内核运行时零填充。 |

节区划分确立了数据的基本存储格局，各变量根据其声明语法完成物理归位：
- **代码指令固化**：函数体内部的运算逻辑被翻译为密集的二进制字节序列并写入 `.text` 节，其内部跳转基于节内相对偏移计算；
- **静态常量权限保护**：类的虚函数表（`vtable`）与 RTTI 类型信息由编译器自动写入 `.rodata` 节，利用操作系统的只读页表映射防止运行期被野指针意外覆写；
- **未初始化数据的零空间保证**：未显式初始化的全局数组（如 `int global_buffer[1024 * 1024]`）在逻辑上内容全为零。若在目标文件中物理写入百万字节的全零数据，会极度浪费磁盘空间。ELF 规范约定此类变量统一归入 `.bss` 节，在目标文件中不占用实际磁盘字节，仅记录运行时所需的内存长度。

### 2.2 跨模块未决占位符

当源码包含跨模块函数调用时，由于独立编译模型的物理隔离，汇编器无法预知被调用实体的内存落点：

```cpp
// 源码：main.cpp
extern void compute_kernel(); // 仅有外部函数签名声明

int main() {
    compute_kernel(); // 跨模块函数调用
    return 0;
}
```

汇编器将 `compute_kernel()` 翻译为目标架构的相对跳转指令序列（在 RISC-V 64 架构下通常采用 `auipc` 与 `jalr` 指令对，汇编助记为伪指令 `call compute_kernel`）。然而，`compute_kernel` 的函数体位于另一个独立的源文件中，其编译生成的机器码最终会被放置在虚拟内存的哪一个绝对地址、与当前调用指令相距多少字节，汇编器完全无法预知。

汇编器无法凭空计算相对跳转偏移，被迫在机器指令的操作数槽位留下全零占位符，并在目标文件中建立重定位记录：

```text
反汇编机器码观察 (riscv64-unknown-linux-gnu-objdump -d -r main.o):
  Disassembly of section .text:
  0000000000000000 <main>:
     0: 1141                 addi   sp, sp, -16
     2: e406                 sd     ra, 8(sp)
     4: 00000097             auipc  ra, 0x0        <-- 预留高 20 位零占位符
                          4: R_RISCV_CALL_PLT compute_kernel
     8: 000080e7             jalr   ra, 0(ra)     <-- 预留低 12 位零占位符
     c: 4501                 li     a0, 0
     e: 60a2                 ld     ra, 8(sp)
    10: 0141                 addi   sp, sp, 16
    12: 8082                 ret
```

汇编器在此处采取了确定性的工程补偿机制：
- **指令立即数槽位占位**：汇编器在 `auipc` 与 `jalr` 指令的立即数字段中暂留全零占位符，使指令流维持 32 位标准定长，保证后续指令的相对偏移不受影响；
- **重定位条目记录**：在目标文件专用的重定位节区（`.rela.text`）中建立显式条目，记录需要修补的节内偏移（`0x4`）、重定位类型（`R_RISCV_CALL_PLT`）以及所绑定的目标符号名称（`compute_kernel`）；
- **单文件编译视界的中断**：汇编器完成了自身视野内的全部翻译工作，但输出的可重定位目标文件（`.o`）因包含未决占位符，处于未完成状态。若强行将其加载至 CPU 执行，该指令将跳转至非法地址触发段错误。

## 3. 静态链接定址

编译阶段生成的各个可重定位目标文件（`.o`）以及系统归档静态库（`.a`），构成了静态链接器（如 `ld.lld` 或 GNU `ld`）的离线输入源。静态链接的核心任务在于打破单一翻译单元的视野隔离，将离散的符号与节区整合进统一步长的虚拟地址空间（VMA）。

链接器扫描所有输入文件的符号表，建立全局符号图谱，将未决函数调用与外部唯一定义完成绑定。随后，链接器将所有目标文件中同属性的节区执行物理归并，为合并后的代码节与数据节分配固定的虚拟运行基地址，并依据重定位条目中的代数公式直接修补机器指令中的全零占位符。

在此基础上，链接器将归并后的节区按照内存访问权限封装为程序头段（Segments），并在磁盘 ELF 文件头部写入程序头部表（Program Header Table），明确声明代码段与数据段预期的内存映射范围与权限标志，生成完整的 ELF 可执行文件。

### 3.1 跨模块符号决议

链接器（`ld` 或 `lld`）接收离散的目标文件列表（`main.o`, `kernel.o`）作为输入。其首要任务是跨模块建立符号映射网格：
- 扫描各个目标文件的符号表（`.symtab`）；
- 抽取所有未决引用的符号条目（节区索引标记为 `SHN_UNDEF`）；
- 在其他目标文件导出的全局符号列表中寻找唯一定义（符号绑定属性为 `STB_GLOBAL` 或 `STB_WEAK`）。

链接器在此阶段执行严格的符号完整性校验：
- **未定义符号拦截**：若某符号在所有目标文件以及引入的静态库中均未检索到有效定义，链接器即刻中断并输出未定义引用错误（`undefined reference to '...'`）；
- **多重定义冲突拦截**：若同一个全局强符号（`STB_GLOBAL`）在多个目标文件中被重复定义，链接器依照单一定义规则（ODR）抛出符号冲突错误（`multiple definition of '...'`）；
- **弱符号覆盖与归并**：若同名符号同时存在全局强符号与弱符号（`STB_WEAK`），链接器优先绑定强符号定义；若仅存在多个弱符号（如模板显式实例化或内联虚函数表），链接器选择保留首个遇到的弱符号实体，静默丢弃其余重复副本。

### 3.2 寻址修补机理

符号决议全部闭合后，链接器打破输入文件间的物理边界，执行第一维度的**同名节区纵向拼接**：
- **同名节区归并**：将所有输入目标文件（`main.o`、`kernel.o` 等）中的代码节拼合为全局单一的 `.text` 节，数据节拼合为单一的 `.data` 节，只读数据节与零初始化节亦同理完成跨文件纵向物理拼接；
- **虚拟基址分配**：依据目标体系结构的虚拟内存模型与链接脚本（Linker Script），为各个合并后的节区分配最终确定的进程虚拟地址（VMA）。

此时，所有全局符号在进程虚拟地址空间中的绝对基址全部确立。链接器遍历各个目标文件遗留的重定位记录（`.rela.text`）：
- 定位待修补机器指令在输出文件中的最终绝对物理偏移；
- 读取目标符号的解析地址，结合当前指令位置计算真实的相对跳转位移；
- **执行二进制覆写，将计算出的目标偏移量写入指令的操作数字段中**（在 RISC-V 体系下，分别提取高 20 位与低 12 位立即数覆写 `auipc` 与 `jalr`，或在符号距离受限时由链接器松弛执行指令消除与压缩折叠）。

经过这一维度的拼接与修补，离散目标文件之间的符号调用被彻底缝合。然而，同名节区的纵向合并仅消除了文件之间的代码碎片；现代 C++ 程序为了支持异常处理展开（`.eh_frame`）、C++ 全局构造函数表（`.init_array`）、动态符号延迟跳转（`.plt` 与 `.got`）以及只读常量保护（`.rodata`），输出文件中依然并存着二三十个功能正交的独立逻辑节区。如何将这数十个功能各异的细粒度节区映射至物理内存，构成了静态链接器必须解决的第二维工程命题。

### 3.3 磁盘静态镜像

完成符号绑定与重定位修补后，链接器将最终产物固化为磁盘上的可执行 ELF 二进制文件。双重视图直接共享同一份底层的机器指令与数据字节，仅是根据不同系统生命周期的使用需求建立的两套索引机制：
- **链接视图（Linking View）**：以**节区（Sections）**为基本组织单元，由文件尾部的**节区头部表（Section Header Table）**统一索引。它细粒度保留了代码、数据与调试符号的独立边界，专供静态链接器、汇编器与 GDB 调试器检索符号定义与源码行号映射；
- **装载视图（Execution View）**：以**段（Segments）**为基本组织单元，由文件头部的**程序头部表（Program Header Table）**统一索引。它将多个内存访问权限相同的相邻节区聚合打包，专供操作系统内核装载器（`execve`）与动态链接器执行高效的内存页表映射。

```text
========================================================================================
                          ELF 二进制双重视图物理分工对照
========================================================================================

  【链接视图 (Linking View)】                             【装载视图 (Execution View)】
  • 核心索引: 节区头部表 (Section Header Table)           • 核心索引: 程序头部表 (Program Header Table)
  • 基本单元: 细粒度节区 (Sections)                       • 基本单元: 粗粒度装载段 (Segments)
  • 核心职责: 支撑编译链接、符号裁决与断点调试            • 核心职责: 指引内核装载、权限隔离与页表映射
  • 服务对象: 静态链接器 (ld) 与调试器 (GDB)              • 服务对象: 操作系统内核 (execve) 与动态链接器
```

> [!NOTE]
> **静态符号表剥离机理**：
> - **静态符号表的物理本质**：静态符号表（`.symtab` 及其字符串表 `.strtab`）详尽记录了源码中定义的局部函数、静态变量以及跨模块全局符号的名称与偏移。在 ELF 节区属性中，该表未设置 `SHF_ALLOC` 标志，属于纯粹的离线元数据，操作系统装载时不会将其映射进进程虚拟内存；
> - **为何能够剥离**：CPU 硬件执行指令时仅依赖机器码中计算确定的物理位移与内存地址，对文本符号名完全无感知。在静态链接修补完重定位操作数后，该表便完成了历史使命；
> - **strip 后的残留实体**：执行 `strip --strip-all ./app`（或 `llvm-strip`）会物理切除节区头部表、静态符号表与 DWARF 调试节区，并将 ELF 头部中的 `e_shoff` 偏移字段置零。此时磁盘镜像中依然完好保留着程序头部表、全部 `PT_LOAD` 代码与数据段，以及运行时必不可少的**动态符号表（`.dynsym` 与 `.dynstr`）**；
> - **为何依然能够执行**：Linux 内核 `load_elf_binary()` 装载时仅解析文件开头的程序头部表，从不读取文件尾部的节区表；程序内部的函数调用依靠机器指令中的确定位移直接寻址，外部动态共享库调用则由保留在内存中的动态符号表驱动。剥离后的二进制文件具备完全等价的执行功能，同时实现了分发体积压缩与符号隐藏。

链接器之所以不直接将这二三十个细粒度逻辑节区逐一暴露给操作系统内核，根本原因在于硬件体系结构的物理限制：
- **硬件页粒度与访问权限**：现代 CPU 的内存管理单元（MMU）以固定大小的虚拟内存页（Page，典型尺寸为 4 KB）作为访问控制的最小物理基准，硬件无法在同一个物理页内为不同字节划分相异的保护权限；
- **内部碎片与页表膨胀**：若单独为仅几十字节的微型节区（如 `.rodata` 或 `.init_array`）开辟独立物理页，将导致页内内存浪费率超过 90%，并迫使内核为每个微型节区维护虚拟内存区域描述符（`vm_area_struct`），引发多级页表膨胀与硬件快表（TLB）击穿开销；
- **第二维横向权限聚合方案**：静态链接器基于“权限相同即合并”的原则，将所有具备相同内存保护权限且生命周期一致的连续节区聚类打包，融合为一个粗粒度的装载段（Segment，类型为 `PT_LOAD`）。

经过静态链接器的打包编排，磁盘上的 ELF 可执行文件呈现出规整的物理段布局，并在装载时整体投射为虚拟内存页面：

```text
========================================================================================
                          ELF 磁盘文件物理镜像与装载映射拓扑图
========================================================================================

    磁盘文件镜像 (File Offset)                                      进程虚拟地址空间 (VMA)
┌────────────────────────────────────────┐
│ ELF 文件头 (ELF Header, 64 字节)       │ ──► 标识文件架构与可执行入口
├────────────────────────────────────────┤
│ 程序头部表 (Program Header Table)      │ ──► 声明装载视图中的所有 Segment 描述符
├────────────────────────────────────────┤
│ 【只读代码段 (PT_LOAD [Flags: R-X])】  │
│   • .text 节区 (CPU 机器执行指令)      │ ──────► 整体对齐映射至只读虚拟代码内存页
│   • .rodata 节区 (字符串与虚函数表)    │         (物理访问权限: 可读、可执行 R-X)
├────────────────────────────────────────┤
│ 【读写数据段 (PT_LOAD [Flags: RW-])】  │
│   • .data 节区 (显式初始化全局变量)    │ ──────► 整体对齐映射至可读写虚拟数据内存页
│   • .init_array 节区 (全局构造指针)    │         (物理访问权限: 可读、可写 RW-)
│   • [注: .bss 节区在磁盘文件中占 0 字节│ ──────► 超出文件大小的差额尺寸，映射为内核零页
├────────────────────────────────────────┤
│ 节区头部表 (Section Header Table)      │ ──► 声明链接视图中的所有 Section 边界 (供 GDB 读取)
└────────────────────────────────────────┘
```

链接器通过这种聚合打包，将离散的数十个逻辑节区紧凑收敛为磁盘上的两类核心 `PT_LOAD` 物理段：只读代码段聚合了可执行指令与只读常量，读写数据段聚合了全局变量、构造指针与零占位的 `.bss`，在满足硬件页级权限隔离的同时，消除了页内碎片并精简了内核页表结构。

## 4. 虚拟空间装载

当用户在 Shell 终端执行可执行文件时，Shell 调用 `fork()` 创建子进程，并在子进程中发起 `execve(2)` 系统调用，CPU 特权级由用户态（U-mode）陷入内核态（S-mode）。

> [!NOTE]
> **`fork()` 与 `execve(2)` 的进程镜像置换**：在 Linux 进程模型中，创建进程与加载程序被严格解耦为两个独立的系统调用。Shell 首先调用 `fork()` 创建子进程（复制父进程上下文并采用写时复制 COW 页表），子进程随即调用 `execve(2)`。`execve` 并不分配新的进程 ID（PID），而是在保留原有 PID、父进程 ID（PPID）以及未设置 `O_CLOEXEC` 标志的打开文件描述符的前提下，在原进程外壳内部彻底释放旧有的用户空间虚拟内存与执行上下文，就地加载全新的 ELF 镜像。

Linux 内核处理 `execve` 的核心入口位于内核源码 `fs/binfmt_elf.c` 中的 `load_elf_binary()` 函数。该例程直接在当前进程的内核栈上下文内运行：首先校验 ELF 文件的头部魔数，随后释放旧进程占用的虚拟内存空间，转而读取当前 ELF 文件的程序头部表。针对每一个类型为 `PT_LOAD` 的装载段，内核创建对应的虚拟内存区域描述符（`vm_area_struct`），并在进程的 RISC-V 64 位（SV39 分页方案）虚拟地址空间中规划标准内存布局：

```text
========================================================================================
                      Linux RISC-V (SV39) 虚拟地址空间段布局图
========================================================================================

  虚拟内存地址 (VA)          内存空间结构与访问权限                      地址增长与动态分配
  ──────────────────────────────────────────────────────────────────────────────────────
  0xFFFF_FFFF_FFFF_FFFF ┌────────────────────────────────────────┐
                        │ 内核空间 (256 GiB, SV39 高半区)        │ S-mode 独占 (U-mode 访问触发异常)
  0xFFFF_FFC0_0000_0000 ├────────────────────────────────────────┤
                        │ 非规范地址空洞 (Canonical Address Hole)│ 硬件未映射区 (访问触发硬件异常)
  0x0000_0040_0000_0000 ├────────────────────────────────────────┤
  0x0000_003F_FFFF_FFFF ├────────────────────────────────────────┤ ◄── 用户栈底 (初始 sp，压入 auxv/envp/argv)
                        │ 用户执行栈 (Stack, Flags: RW-)         │   │
                        │                                        │   ▼ 栈帧随调用向下增长 (sp 向低地址扩展)
                        ├ · · · · · · · · · · · · · · · · · · · ·┤
                        │ 自由内存留白区 (Unmapped Gap)          │
                        ├ · · · · · · · · · · · · · · · · · · · ·┤
                        │ 动态内存映射区 (mmap / 共享库 .so)     │   ▲
                        │                                        │   │ 映射区通常自顶向下分配
                        ├────────────────────────────────────────┤
                        │ 运行时堆区 (Heap, Flags: RW-)          │   ▲
                        │                                        │   │ 堆随 brk/sbrk 向高地址向上增长
  0x0000_0000_0002_0000 ├────────────────────────────────────────┤ ◄── 堆底基址 (起始 brk 指针)
                        │ 读写数据段 (.data / .bss, Flags: RW-)  │ ◄── PT_LOAD Segment 1 (静态初始化与零页)
  0x0000_0000_0001_0000 ├────────────────────────────────────────┤ ◄── 代码段加载基址
                        │ 只读代码段 (.text / .rodata, Flags: R-X│ ◄── PT_LOAD Segment 0 (指令流与只读常量)
  0x0000_0000_0000_0000 ├────────────────────────────────────────┤
                        │ 零页保留区 (捕捉 NULL 空指针非法解引用)│ 操作系统映射为只读保护，禁止写与执行
                        └────────────────────────────────────────┘
  ──────────────────────────────────────────────────────────────────────────────────────
  ▲ 低地址 (0x0)                                                            高地址 ▲
```

### 4.1 虚存映射机制

内核针对每一个 `PT_LOAD` 段执行虚拟内存区域（VMA）的构建：
- 读取该段的虚拟起始地址（`p_vaddr`）、文件镜像大小（`p_filesz`）与内存驻留大小（`p_memsz`）；
- 在内核进程控制块中开辟对应的虚存描述结构（`vm_area_struct`），通过系统内部机制将磁盘文件偏移与虚拟地址区间建立绑定关系。

> [!NOTE]
> **延迟分页与 BSS 匿名零页机制**：装载过程并不真正将磁盘上的整个程序拷贝进物理内存。内核仅在页表中建立虚拟内存区间与磁盘文件块的映射。只有当 CPU 首次执行跳转到某一虚拟页并触发硬件缺页异常（Page Fault）时，操作系统才按需分配物理页框并将代码调入内存。对于内存驻留大小大于文件镜像大小的差额部分（`p_memsz > p_filesz`，即未初始化的 `.bss` 节），内核为其建立匿名虚拟内存映射（Anonymous VMA），利用写时复制（COW）映射系统的全局只读零页（`ZERO_PAGE`）。当程序首次执行写入操作触发缺页异常时，操作系统才实际分配物理页框，实现只消耗虚拟地址而不占用磁盘空间的物理保证。

### 4.2 用户堆栈初始化

虚拟内存布局确立后，内核在虚拟空间的高地址区域为进程开辟用户态执行栈，并按照操作系统 ABI 规范在栈底压入初始运行上下文：

```text
高地址
┌─────────────────────────────────────────────────────────────┐
│ 环境变量字符串与参数字符串存储区                            │
├─────────────────────────────────────────────────────────────┤
│ 辅助向量表 (Auxiliary Vectors, auxv: 页面大小、平台特征等)   │
├─────────────────────────────────────────────────────────────┤
│ 环境变量指针数组 (envp 数组，以 NULL 指针结尾)              │
├─────────────────────────────────────────────────────────────┤
│ 命令行参数指针数组 (argv 数组，以 NULL 指针结尾)            │
├─────────────────────────────────────────────────────────────┤
│ 命令行参数个数 (argc, 8 字节整数)                           │ <── 初始用户栈指针 (sp)
└─────────────────────────────────────────────────────────────┘
低地址 (栈向下增长)
```

栈底数据的物理装配完成以下上下文传递：
- 压入命令行参数个数 `argc` 与对应的参数字符串指针数组 `argv`；
- 压入系统环境变量指针数组 `envp`；
- 压入辅助向量表（Auxiliary Vectors, `auxv`），向用户空间传递系统物理页大小、硬件体系结构特征标号以及动态链接器自身的装载基地址。

## 5. 运行时环境就绪

操作系统内核完成页表映射与栈底初始化后，交付给用户空间的仅仅是一片未加工的裸机硬件环境。此时内存中尚不存在任何高级语言的运行实体：没有建立 C 语言函数调用栈帧，没有对齐硬件堆栈，更没有构造任何 C++ 全局对象。

从计算机体系结构视角审视，内核交付的真实入口 `_start` 本质上依然属于纯粹的汇编代码领域——它不是一个合法的 C/C++ 函数，没有调用者返回地址，不能执行 `ret` 语句返回，更无法直接理解高级语言的变量与对象语法。然而，用户编写的业务逻辑必须以高级语言函数（`main()`）的形式启动。

进入高级编程语言世界的唯一物理通道，是发起一次符合规范的函数调用；而函数调用的物理基石，正是目标体系结构的调用规约（Calling Convention，即 RISC-V ELF psABI）。高层语言函数对于执行现场有着严格的物理契约：传参寄存器必须按规约装配完毕、栈指针必须满足硬件对齐约束、外部依赖符号必须完成物理跳转绑定。这一物理鸿沟，要求系统在进入用户业务函数之前，必须由汇编跳板跨越边界，遵照调用规约发起程序生命周期中的首个正规函数调用，对应运行时入口跳跃（5.1 节）；并在进入高级语言世界后，遵照函数调用链完成全局对象的生命周期装配，对应全局构造链执行（5.2 节）。

### 5.1 运行时入口跳跃

内核完成虚拟地址空间映射与栈底初始化后，通过修改保存的硬件寄存器现场，促使 CPU 由内核态（S-mode）返回用户态（U-mode）执行。此时首条指令的着陆点依据程序的链接属性发生物理分流：
- **动态链接程序（带有 `PT_INTERP` 段）**：内核读取 ELF 解释器段声明的路径字符串（如 `/lib/ld-linux-riscv64-lp64d.so.1`），为动态链接器单独建立虚拟内存映射，并将首条用户指令指针强行扭转指向动态链接器的代码入口。动态链接器接管控制权后，读取本程序 `.dynamic` 节中的 `DT_NEEDED` 条目，递归装载所有依赖的共享库（`.so`），并对数据段中的全局偏移表（GOT）完成符号填补；
- **静态链接程序（无 `PT_INTERP` 段）**：内核直接将首条指令指针指向 ELF 头部记录的程序自身入口点。

动态链接完成后，控制权最终交还给可执行文件自身在 ELF 头部声明的真实汇编入口地址 **`_start`**（位于 glibc 提供的 `crt1.o` 启动代码中）。此时，`_start` 汇编逻辑扮演了从裸机数据跨入高级语言调用规约的转换桥梁：

```text
反汇编观察 (glibc 体系结构启动桩 sysdeps/riscv/start.S):
  _start:
     # 1. 从裸机栈上提取原始数据并转入 psABI 规约传参寄存器
     ld    a1, 0(sp)             # 从栈顶提取 argc 存入参数寄存器 a1
     addi  a2, sp, 8             # 计算 argv 指针存入参数寄存器 a2

     # 2. 建立符合调用规约的硬件物理堆栈契约
     andi  sp, sp, -16           # 强制将栈指针向低地址按照 16 字节对齐

     # 3. 遵照调用规约装配首个高级语言函数调用的实参列表
     lla   a0, main              # 将 main 函数指针作为参数 1 放入寄存器 a0
     lla   a3, __libc_csu_init   # 传入全局构造初始化函数指针放入 a3
     lla   a4, __libc_csu_fini   # 传入全局析构终止函数指针放入 a4
     mv    a5, a6                # 传入动态链接器终结函数指针放入 a5

     # 4. 正式发起跨界函数调用，跃入 C 语言世界
     call  __libc_start_main     # 跨越汇编与 C 语言边界，建立首个函数栈帧
     call  abort                 # 若 __libc_start_main 异常返回则强制终止
```

> [!NOTE]
> **16 字节栈对齐与 RVV 向量硬件对齐契约**：RISC-V ELF psABI 强制要求在发起函数调用（`call` / `jalr`）时，栈指针 `sp` 必须始终保持 16 字节物理对齐（`sp % 16 == 0`）。其硬件根因在于现代 RISC-V 处理器广泛配备双精度浮点（RV64D）与向量扩展（RVV），执行宽位宽内存操作指令（如 `vle64.v` 向量加载与 `fld` 浮点加载）。硬件访存部件要求栈内存基准地址按 16 字节严格对齐；若 `_start` 未完成对齐，后续向量或浮点指令在访问未对齐的栈内存时，将触发硬件对齐异常（Load/Store Address Misaligned Trap）导致内核信号中断或极高昂的软件模拟开销。

### 5.2 全局构造链执行

`__libc_start_main` 接管后，构筑起最终的安全运行环境：
- 注册信号处理管道与异常分发机制；
- 将 `main()` 自身的函数指针记录于内部上下文；
- **按顺序遍历 `.init_array` 节区中的函数指针数组**。

编译器在处理 C++ 代码中的全局类对象或文件作用域静态对象时，会自动生成其构造调用桩代码，并将这些桩函数的地址按编译依赖顺序排列在可执行文件的 `.init_array` 节中。`__libc_start_main` 沿着该数组依次调用每个函数指针，完成全局变量、标准 I/O 对象（如 `std::cout`）以及跨模块单例的内存构造。

动态重定位完成，GOT 表项填充完毕，`.init_array` 中的构造函数指针按序执行完毕。进程的软硬件执行环境至此彻底对齐，运行时正式移交控制权，引导 CPU 跃入用户业务入口：

```text
result = main(argc, argv, envp);
```

控制权正式交由用户的业务主函数。

## 6. 运行时销毁退出

当用户业务函数 `main()` 执行完毕并返回整型退出状态码时，控制权返回至 `__libc_start_main()` 的调用栈中，程序的生命周期进入终止清理阶段。

这一阶段由用户态与内核态两个物理层次协作完成：首先由用户态 C 运行时执行应用层语义实体的析构与文件数据冲刷，随后发起系统调用，交由操作系统内核彻底回收底层的硬件虚拟内存、文件句柄与进程控制块（PCB）。

### 6.1 析构时序

`main()` 中的 `return code;` 语句本质上被编译器编译为普通的局部栈帧清理与寄存器返回值设置。当 `main()` 返回时，整型退出状态码由 CPU 通用寄存器（RISC-V 架构下为 `a0` / `x10`）暂存，控制权落回到 `__libc_start_main` 的栈帧中：
- 运行时捕获返回值，将其作为参数隐式调用标准 C 库退出函数 **`exit(result)`**；
- `exit()` 首先**逆序遍历 `.fini_array` 节区中的函数指针数组**，依次触发全局对象与静态对象的析构函数，完成内存资源的回收；
- 执行通过 `atexit()` 显式注册的全部用户退出钩子函数；
- 冲刷所有打开的标准 I/O 缓冲区，确保残留在用户空间内存中的输出数据全部强制刷盘写回文件系统。

### 6.2 资源回收

在用户空间的所有痕迹被清理后，`exit()` 发起最后的内核系统调用 **`_exit(2)`**（或 `exit_group(2)`）：
- CPU 再次由用户态陷入内核态；
- 操作系统内核释放该进程占用的全部虚拟内存区域（销毁页表与 `mm_struct`），关闭所有未关闭的文件描述符；
- 进程的运行状态被重写为 `TASK_DEAD`（僵尸态 Zombie），其物理资源除进程控制块（`task_struct`）外全部释放，保留退出状态码供父进程查询；
- 内核向父进程发送 `SIGCHLD` 信号。父进程通过调用 `wait()` 或 `waitpid()` 读取该状态码后，内核彻底注销该进程控制块，分配的 PID 被系统收回。

> [!NOTE]
> **`exit(3)` 库函数与 `_exit(2)` 系统调用的缓冲区分界**：标准 C 库函数 `exit()` 属于用户态流程，其核心安全职责在于遍历 `.fini_array` 析构对象并调用 `fflush()` 强制冲刷所有标准 I/O 缓冲区；而 `_exit(2)`（或 C99 的 `_Exit()`）是直接陷入内核态的系统调用，它立即释放进程虚拟内存并终止执行，绝不执行任何析构函数，也绝不冲刷用户态缓冲区。若程序在存在未落盘数据时直接调用 `_exit(2)`，残留在用户内存缓冲区中的数据将永久丢失。此外，进程终止后保留为僵尸态（`TASK_DEAD`），直到父进程调用 `waitpid()` 读取退出状态后才注销进程控制块（PCB）；若父进程先于子进程终止，子进程将被系统 1 号进程（`systemd` 或 `init`）收养并由其代为回收资源。

至此，程序在物理世界中的生命周期完成了对称收敛的完整闭环。
